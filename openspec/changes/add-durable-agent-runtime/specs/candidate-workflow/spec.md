## MODIFIED Requirements

### Requirement: WF-020 [CONFIRMED] Минимальная машина состояний
Workflow SHALL поддерживать состояния `NEW`, `WAITING_FOR_STABILITY`, `MATERIALS_INCOMPLETE`, `MATERIALS_READY`, `TRANSCRIBING`, `ANALYZING`, `VALIDATING`, `WAITING_FOR_HUMAN`, `READY` и `FAILED`. `WAITING_FOR_HUMAN` MUST означать, что runtime сохранил продолжимый run и сформировал содержательную escalation с конкретным разрешённым действием человека. `FAILED` MUST использоваться только для терминального исхода, когда автоматическое продолжение исчерпано и допустимое действие человека не определено либо policy запрещает продолжение. Оба состояния MUST сопровождаться этапом, кодом причины, числом attempts и безопасным evidence; отдельные технические причины MUST NOT требовать других верхнеуровневых состояний кандидата.

#### Scenario: Кандидат проходит штатную обработку
- **WHEN** полный стабильный комплект обрабатывается без ошибок
- **THEN** переходы проходят через применимые состояния от `NEW` до `READY`
- **AND** система не пропускает обязательные этапы

#### Scenario: Автоматические повторы исчерпаны
- **WHEN** сбойный этап выполнил все разрешённые attempts и runtime определил допустимое действие человека
- **THEN** кандидат переходит в `WAITING_FOR_HUMAN`
- **AND** escalation однозначно описывает причину, уже выполненные действия и способ продолжения

#### Scenario: Обязательный файл невозможно обработать
- **WHEN** присутствующее резюме или запись интервью повреждены, имеют неподдерживаемый формат либо не могут быть разобраны
- **THEN** кандидат переходит в `WAITING_FOR_HUMAN` без бессмысленного автоматического повтора
- **AND** система сохраняет файл, этап и код причины, не публикует частичный отчёт или уведомление об успехе и предлагает HR заменить конкретный файл

#### Scenario: Препятствие терминально
- **WHEN** автоматические recovery paths исчерпаны и разрешённое действие человека отсутствует
- **THEN** кандидат переходит в `FAILED`
- **AND** терминальная причина отличается от содержательной human escalation

### Requirement: WF-021 [CONFIRMED] Аудит переходов состояния
Для каждого перехода система SHALL сохранять абсолютное время в UTC ISO 8601, причину, attempt, plan version, trigger/event identity, actor либо worker identity и безопасную техническую ошибку при её наличии. Для repair, replan, escalation и resume аудит MUST дополнительно связывать obstacle, прежнее и новое решение, reused artifacts, budget usage и evidence. Отображение времени MUST использовать настроенную IANA-зону `Asia/Yekaterinburg` и явное смещение `+05:00`, не изменяя сохранённое значение UTC.

#### Scenario: Этап завершился ошибкой
- **WHEN** кандидат переводится в `WAITING_FOR_HUMAN` либо `FAILED`
- **THEN** запись перехода содержит stage, time, reason, attempt, plan version и безопасную техническую ошибку
- **AND** при escalation содержит ссылку на разрешённое действие человека

#### Scenario: Runtime изменил план
- **WHEN** obstacle приводит к replan
- **THEN** аудит связывает обе plan versions, obstacle, использованный budget и reused artifacts
- **AND** прежний plan остаётся неизменным

### Requirement: WF-023 [CONFIRMED] Безопасный повтор этапов
Ошибочный task SHALL допускать ограниченный автоматический retry, repair и replan по agent-runtime policy и явное действие HR без повторения уже завершённых совместимых дорогих операций, если входные и profile versions не изменились. Разрешение escalation без изменения immutable inputs SHALL продолжать тот же run. Терминальный ручной повтор или изменение input/profile version MUST создавать новый run по применимым правилам WF-014 и WF-031.

#### Scenario: AI-анализ повторяется после транскрибации
- **WHEN** analysis task завершился ошибкой, а входные файлы и transcript checkpoint неизменны
- **THEN** recovery использует сохранённую стенограмму
- **AND** не отправляет аудио на повторную транскрибацию

#### Scenario: HR повторяет терминально сбойный этап
- **WHEN** кандидат находится в `FAILED`, входные версии не изменились и HR запускает новый анализ
- **THEN** система создаёт новый run, начинающийся с применимого сбойного этапа
- **AND** сохраняет ссылки на совместимые результаты прежнего run

#### Scenario: HR заменяет необрабатываемый обязательный файл
- **WHEN** кандидат находится в `WAITING_FOR_HUMAN` из-за повреждённого или неподдерживаемого обязательного файла и HR заменяет этот файл
- **THEN** система создаёт новую версию входного комплекта по WF-014
- **AND** после стабилизации полного комплекта новый run связывается с исходной escalation

#### Scenario: Повтор после неподдерживаемой AI-схемы
- **WHEN** analysis завершился `UNSUPPORTED_SCHEMA_VERSION`, configuration исправлена, а inputs, OCR и transcript не изменились
- **THEN** разрешённый recovery начинает AI-анализ заново и выполняет последующие этапы
- **AND** не повторяет извлечение документов, OCR или транскрибацию

#### Scenario: HR разрешает obstacle без изменения входов
- **WHEN** кандидат находится в `WAITING_FOR_HUMAN` и HR выбирает допустимое действие, не меняющее input/profile versions
- **THEN** тот же run продолжается с указанного task
- **AND** сохраняет прежние budget usage, checkpoints и completed artifacts

## ADDED Requirements

### Requirement: WF-040 [CONFIRMED] Очередь показывает содержательную escalation
Для кандидата в `WAITING_FOR_HUMAN` интерфейс SHALL показывать понятное описание препятствия, stage, влияние на результат, выполненные автоматические действия, безопасное evidence, сохранённые artifacts и конкретные разрешённые действия HR. Общая надпись `FAILED` или предложение повторить весь процесс MUST NOT заменять эти сведения.

#### Scenario: HR открывает кандидата с escalation
- **WHEN** run ожидает замены повреждённого интервью
- **THEN** интерфейс указывает конкретный файл и причину
- **AND** объясняет, что transcript отсутствует, а уже извлечённое резюме будет переиспользовано

#### Scenario: Escalation устарела
- **WHEN** HR пытается выполнить действие для неактуальной escalation version
- **THEN** система отклоняет действие без изменения run
- **AND** показывает текущее препятствие и доступные действия
