## MODIFIED Requirements

### Requirement: WF-010 [CONFIRMED] Минимальный комплект
Минимальный комплект для автоматического запуска SHALL состоять из резюме и как минимум одного источника интервью вне каталога `Результаты/`: поддерживаемой аудио-/видеозаписи либо готовой стенограммы в текстовом формате или DOCX. Готовая стенограмма MUST распознаваться по transcript-like имени как интервью-материал, а не как резюме или дополнительный документ. DOCX рекомендаций/характеристик MUST оставаться поддерживаемым дополнительным документом. Несколько записей и/или готовых стенограмм одного кандидата MUST включаться в один immutable input manifest и обрабатываться без выбора или отбрасывания источника.

#### Scenario: Резюме и готовая стенограмма присутствуют без записи
- **WHEN** стабильный комплект содержит резюме и одну поддерживаемую готовую текстовую стенограмму, но не содержит аудио или видео
- **THEN** система признаёт минимальный комплект полным
- **AND** запускает обычный candidate workflow

#### Scenario: Оба обязательных материала присутствуют
- **WHEN** стабильный комплект содержит резюме и одну поддерживаемую запись интервью
- **THEN** система признаёт минимальный комплект полным

#### Scenario: Есть несколько записей и готовых стенограмм
- **WHEN** стабильный комплект содержит более одного источника интервью
- **THEN** система признаёт комплект полным
- **AND** обрабатывает каждый источник с отдельной provenance

### Requirement: WF-011 [CONFIRMED] Недостаточно материалов
При отсутствии резюме или хотя бы одного поддерживаемого источника интервью система SHALL присваивать состояние `MATERIALS_INCOMPLETE`, отображаемое пользователю как `Недостаточно материалов`, и перечислять недостающие материалы. Источником интервью может быть аудио-/видеозапись либо готовая текстовая стенограмма. Наличие дополнительных interview-source не является ошибкой комплектности. В этом состоянии анализ MUST NOT запускаться. Присутствующий, но пустой, повреждённый либо неподдерживаемый файл MUST завершать соответствующую стадию типизированной ошибкой и MUST NOT оставлять кандидата бесконечно ожидающим обработку.

#### Scenario: Нет ни записи, ни готовой стенограммы
- **WHEN** стабильная папка содержит резюме, но не содержит поддерживаемый источник интервью
- **THEN** кандидат получает состояние недостатка материалов
- **AND** сообщение указывает отсутствие записи или готовой стенограммы

#### Scenario: Нет записи интервью
- **WHEN** стабильная папка содержит резюме, но не содержит ни поддерживаемую запись, ни готовую текстовую стенограмму
- **THEN** кандидат получает состояние недостатка материалов
- **AND** сообщение явно указывает допустимые альтернативы интервью-материала

### Requirement: WF-030 [CONFIRMED] Последовательность основного процесса
Основной процесс SHALL обнаружить папку или изменение; связать её с вакансией и кандидатом; дождаться стабильности; проверить комплект; зафиксировать версии и SLA; получить или лениво скомпилировать единую компактную матрицу `profileVersion`; извлечь текст резюме; получить нормализованную стенограмму из записи либо готового текста; разделить материалы на batches с overlap; выполнить coverage extraction по каждому `criterionId`; объединить сведения и выполнить один gap-search для пустых критериев; заполнить каждую строку ровно один раз; при необходимости мягко перепроверить только стоп-фактор или существенно отказной вывод; целостно сформировать рекомендацию; проверить техническую согласованность; сохранить отчёт и уведомить HR. Ошибка вспомогательной критики, open pass, gap-search или verification MUST NOT останавливать формирование результата.

#### Scenario: Полный комплект проходит обработку
- **WHEN** кандидат достигает `MATERIALS_READY`
- **THEN** система выполняет обязательные этапы в указанной зависимости
- **AND** публикует результат только после проверки полноты матрицы, доказательств и provenance

#### Scenario: Матрица профиля ещё компилируется
- **WHEN** кандидат готов к анализу, но shared-компиляция его `profileVersion` не завершена
- **THEN** запуск ожидает тот же matrix artifact без создания конкурирующей матрицы

## ADDED Requirements

### Requirement: WF-040 Совместимость legacy-запусков
Запуски, начатые до включения matrix-driven routing, MUST завершаться по зафиксированной workflow version. Готовые результаты MUST NOT пересчитываться, а ручной повтор MUST создавать новый result version по действующему workflow и сохранять прежний результат.

#### Scenario: Feature flag переключён во время анализа
- **WHEN** legacy-запуск уже зафиксировал workflow version
- **THEN** он завершает прежний путь без смешивания артефактов двух workflow

### Requirement: WF-041 Version-safe selective recovery
Ручной повтор failed run MUST переиспользовать только непрерывный префикс успешных стадий при точном совпадении `inputVersion`, `profileVersion`, goal type, workflow version и policy version. Для каждой reused стадии MUST существовать lineage-доступный artifact ожидаемого provenance и совместимой schema family. Первая failed, отсутствующая либо несовместимая стадия MUST стать первой `RUNNABLE`; все последующие стадии MUST выполняться заново. Успешный ранее завершённый run MUST начинать полный новый анализ.

#### Scenario: Ошибка произошла при PDF
- **WHEN** failed `matrix-v3` run имеет совместимые artifacts до validation включительно
- **THEN** successor переиспользует этот непрерывный префикс и начинает с reports

#### Scenario: Повтор старого matrix-v2 после обновления
- **WHEN** действующий workflow равен `matrix-v3`, а failed predecessor имеет `matrix-v2`
- **THEN** candidate-scoped checkpoints predecessor не переиспользуются и новый run начинает полный `matrix-v3` анализ

#### Scenario: Artifact успешной задачи отсутствует
- **WHEN** задача predecessor имеет `SUCCEEDED`, но ожидаемый artifact отсутствует или имеет несовместимую schema
- **THEN** эта задача и весь её downstream выполняются заново

### Requirement: WF-042 Фиксация входов начатого запуска
После создания candidate run все стадии MUST читать только immutable material manifest связанной `inputVersion`. `candidate.drive-snapshot/v1` MUST воспроизводить зафиксированный snapshot и MUST NOT повторно подменять его текущим содержимым папки. Добавленный, удалённый или изменённый после старта файл MUST относиться только к следующей input version; само его появление MUST NOT останавливать уже начатый run.

#### Scenario: Новый файл добавлен до выполнения drive-snapshot task
- **WHEN** run уже создан для полной стабильной input version, а HR добавил файл до исполнения первой задачи
- **THEN** drive-snapshot и все downstream стадии текущего run используют прежний manifest
- **AND** новый файл обнаруживается отдельно как следующая версия материалов

### Requirement: WF-043 Актуализация материалов перед ручным повтором
Каждый принятый ручной повтор MUST сначала заново получить из папки кандидата полный стабильный snapshot и только после этого создавать successor run. Система MUST сравнивать файлы как минимум по `fileId` и provider version, а не только по имени или размеру. Если актуальный manifest полностью совпадает с manifest failed predecessor, система MAY переиспользовать его `inputVersion` для version-safe selective recovery. Если файл добавлен, удалён либо изменена его provider version, система MUST создать новую immutable `inputVersion`, запретить reuse candidate-scoped стадий predecessor и запустить анализ по обновлённым материалам. После создания successor run действует WF-042: последующие изменения папки в него не попадают.

#### Scenario: Перед повтором добавлен новый материал
- **WHEN** HR добавил файл в папку кандидата и запросил повторную обработку
- **THEN** система дожидается стабильности нового состава папки
- **AND** создаёт successor run с новой `inputVersion`, manifest которой содержит добавленный файл

#### Scenario: Файл изменён без изменения размера
- **WHEN** перед ручным повтором provider version файла изменилась, а размер остался прежним
- **THEN** система считает состав входов изменённым
- **AND** не переиспользует прежнюю `inputVersion` или candidate-scoped checkpoints

#### Scenario: Материалы не изменились после failed run
- **WHEN** свежий стабильный snapshot в точности совпадает с manifest failed predecessor
- **THEN** successor MAY использовать ту же `inputVersion`
- **AND** version-safe selective recovery продолжает работу с первой непройденной стадией
