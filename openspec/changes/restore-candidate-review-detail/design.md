## Context

См. `proposal.md`. Текущая карточка реализована в крупном клиентском модуле и получает product projection, где часть assessment/evidence данных уже присутствует под техническими ключами. Существующий change `add-in-app-report-preview` отдельно регулирует актуальную пару PDF и не должен быть переопределён. Main specs остаются нормативными; демо-сессия используется как визуальный ориентир, а не источник требований.

## Goals / Non-Goals

**Goals:**

- Ввести явную UI-модель подробного результата, не зависящую от сырых имён полей provider/schema.
- Восстановить стабильную композицию секций и адаптивную двухколоночную раскладку демо-интерфейса.
- Сохранить version-bound поведение текущей сводки и PDF preview.
- Сделать состояния отсутствия, обработки и ошибки тестируемыми и различимыми.
- Восстановить информационную иерархию списка вакансий и двойное состояние верхней панели по пользовательским скриншотам.
- Показывать согласованный расчётный индекс ABC без представления его как вероятности или confidence.

**Non-Goals:**

- Изменение алгоритма оценки, генерации PDF, workflow state machine или истории версий.
- Добавление редактирования результатов HR.
- Точное пиксельное копирование временного demo deployment.

## Decisions

### 1. Нормализованная view model между product projection и компонентом

Серверная или чистая shared-функция формирует version-bound `CandidateReviewDetail`: recommendation, ABC directions, отдельные assessment sections, evidence items, source materials и result descriptors. Компонент не читает произвольные object keys и не превращает их в текст напрямую. Это выбирается вместо локального набора условных JSX-веток, поскольку единый mapping можно контрактно тестировать и переиспользовать в rendered tests.

### 2. Закрытый словарь человекочитаемых типов с безопасным fallback

Известные типы доказательств и состояний отображаются через централизованный словарь. Для неизвестного валидного типа используется нейтральная подпись `Доказательство`, а исходный ключ остаётся только в данных/диагностике. Автоматическое преобразование snake_case в заголовок отклонено: оно продолжает раскрывать внутреннюю модель и даёт плохие русские подписи.

### 3. Семантические компоненты секций вместо универсальной карточки значений

Recommendation, ABC grid, assessment outcome, evidence list и materials/results получают отдельные компоненты с общим визуальным каркасом. Это сохраняет разную семантику и состояния при едином стиле. Один универсальный renderer отклонён, потому что именно он склонен смешивать блоки и одинаково трактовать отсутствие данных.

### 4. CSS Grid с последовательным narrow layout

На desktop основная колонка содержит оценку и доказательства, боковая — материалы/результаты; на narrow viewport боковая колонка становится последней секцией основного потока. Контент использует `minmax(0, 1fr)`, перенос длинных строк и отсутствие фиксированных ширин. Скрытие или горизонтальная прокрутка карточки не допускаются.

### 5. Тесты сначала и независимый автор приёмки

Независимый субагент создаёт TST-079 до реализации и фиксирует ожидаемый RED. Основная реализация затем проходит focused unit/rendered/acceptance проверки, `npm test`, lint и полный обязательный E2E-набор согласно `AGENTS.md`.

### 6. Один чистый расчёт ABC-индекса

Чистая функция преобразует каждую валидную оценку в `A=100`, `B=70`, `C=40` и округляет среднее арифметическое. Одна и та же функция используется в верхней панели готового кандидата, боковой оценке и таблице кандидатов. Функция не получает workflow progress, ETA или evidence confidence и возвращает отсутствие значения для пустого/невалидного профиля.

### 7. Два режима верхней панели и шестишаговый timeline

`READY` hero показывает расчётный индекс и рекомендацию. Processing hero показывает сохранённый progress, milestone/status и ETA. Timeline отображает шесть пользовательских шагов, а статусы только сопоставляются с ними; UI не создаёт progress или elapsed локально.

### 8. Предметная проекция решения и доказательств

Repository строит summary из наблюдений актуального assessment и связывает каждый evidence fact с ABC/компетенцией/риском/стоп-фактором/условием КЕ через `factIds`. Отдельная неподписанная выдача допускается только как `Дополнительные доказательства` с явной связью `Общий анализ`. Materials renderer не создаёт fallback-файлы.

## Risks / Trade-offs

- [Существующая проекция не содержит раздельных данных] → Расширить только безопасную version-bound проекцию и не восстанавливать отсутствующие выводы из PDF или сырых LLM traces.
- [Неизвестные типы потеряют специфичность] → Использовать нейтральный fallback и дополнять закрытый словарь отдельными проверяемыми изменениями.
- [Большая карточка станет визуально тяжёлой] → Сохранять компактные заголовки и карточки, но не сворачивать нормативные секции по умолчанию.
- [Процент будет принят за вероятность] → Называть его расчётным индексом ABC в `aria-label`/подсказке, не использовать слово confidence и не сортировать кандидатов автоматически.
- [Регрессия PDF preview] → Не менять result descriptors/modal contract и повторно запускать TST-077/TST-078 вместе с TST-079.

## Migration Plan

1. Добавить RED-приёмку на синтетических данных без изменения production fixtures.
2. Ввести нормализованную view model и mapping технических типов.
3. Перевести карточку на новые секционные компоненты и адаптивную раскладку.
4. Запустить focused проверки, затем полный regression/E2E gate на одной сборке.
5. Развёртывание не требует миграции хранилища, если текущая projection полна; при расширении API добавить поля обратно совместимо.
6. Rollback выполняется возвратом UI/view-model изменений без изменения сохранённых результатов и PDF.
