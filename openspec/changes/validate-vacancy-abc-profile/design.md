## Context

Proposal вводит новую capability `vacancy-profile`, а delta spec содержит её полный нормативный baseline с сохранёнными идентификаторами и статусами решений. Наличие требования в baseline описывает целевое обязательное поведение, но не означает, что всё оно уже реализовано текущим прототипом.

Implementation slice этого change ограничен проверкой ABC-направлений при сохранении: сценариями нормализованной уникальности из `VAC-017` и полноты, сохранения черновика и изменения версии из `VAC-019`. Текущий `VacancySettings` хранит направления и отображаемый номер версии в локальном React state, проверяет только пустые и повторяющиеся названия, сообщает об ошибках кратким уведомлением и принимает черновики с пустыми A/B/C либо без направлений.

## Goals / Non-Goals

**Goals:**

- Зафиксировать полную самодостаточную спецификацию capability, пригодную для последующих changes без внешнего нормативного источника.
- Сохранить стабильные идентификаторы и явный статус `CONFIRMED` или `TBD`.
- Сделать правила ABC-валидации детерминированными и независимо тестируемыми.
- Возвращать структурированные ошибки с указанием направления и поля.
- Показывать постоянную обратную связь рядом с невалидными элементами управления.
- Не менять черновик и отображаемую версию после отклонённого сохранения.
- Сохранить существующий успешный save flow после прохождения проверки.

**Non-Goals:**

- Реализовывать в этом change остальные требования baseline: постоянное хранение, активацию, аудит, полный профиль, LLM-генерацию или распространение вакансии по всем потребителям.
- Автоматически исправлять или дополнять пустые определения демонстрационных профилей.
- Вводить общий form framework, новую schema-validation библиотеку или backend API.
- Принимать решения, помеченные `TBD`.

## Decisions

### Полный baseline отделён от implementation slice

Delta spec переносит capability целиком, чтобы после архивации OpenSpec содержал самостоятельный контракт. В tasks входят только сценарии `VAC-017` и `VAC-019`, заявленные как текущий implementation slice. Остальные требования сохраняются как известный целевой baseline и реализуются отдельными changes.

Альтернатива — перенести только ABC-валидацию — оставила бы capability частичной и потребовала бы продолжать обращаться к другому нормативному источнику.

### Использовать чистый валидатор со структурированными ошибками

ABC-правила реализуются как чистая TypeScript-функция, принимающая упорядоченный список направлений и возвращающая успешный результат либо набор ошибок. Ошибка содержит стабильный идентификатор направления при применимости, поле `collection`, `name`, `gradeA`, `gradeB` или `gradeC` и пользовательское сообщение.

Проверки непосредственно внутри обработчика кнопки рассматривались, но сохранили бы связанность правил, UI-feedback и изменения версии и усложнили бы изолированные тесты.

### Нормализация применяется только для проверки

Для проверки заполненности и уникальности названия очищаются от окружающих пробелов и сравниваются без учёта регистра. Валидатор не переписывает исходные значения. Это сохраняет введённый HR черновик без скрытых изменений после ошибки.

Автоматическое исправление значений при сохранении отклонено: оно не требуется контрактом и нарушает наблюдаемое сохранение черновика.

### Полная проверка выполняется на границе сохранения

Во время редактирования допускаются неполные направления. Весь список проверяется при действии `Сохранить новую версию`. Ошибки затронутого поля очищаются либо пересчитываются после его редактирования, но само редактирование не создаёт версию.

Постоянно отключённая кнопка сохранения отклонена, потому что она скрывает причину невалидности и не обеспечивает требуемый сценарий отклонённой попытки.

### Использовать inline feedback и краткое резюме сохранения

Каждая field-level ошибка связывается с соответствующим input или textarea и отмечает элемент как невалидный. Collection-level feedback используется при отсутствии направлений. Первая ошибка дополнительно выводится через существующий механизм уведомлений.

Только transient notification недостаточен: он исчезает и не остаётся связанным с полем, которое нужно исправить.

### Версия изменяется только после успешной проверки

Save handler сначала запускает валидатор и при наличии ошибок завершает действие без изменения версии и без успешного уведомления. При валидном результате устаревшие ошибки очищаются, а существующее успешное действие выполняется ровно один раз.

Текущий change не заявляет durable version creation. Переход от локального действия к постоянному хранению будет отдельным change, реализующим соответствующие требования baseline.

### Приёмочный RED создаётся независимо до реализации

Независимый субагент сначала создаёт исполняемый приёмочный тест по сценариям `VAC-017` и `VAC-019` и фиксирует ожидаемое падение. После реализации focused unit и UI tests проверяют валидатор, feedback, сохранение черновика и изменение версии. Полный обязательный регрессионный набор остаётся release gate; отсутствующий тест нельзя считать пройденным.

## Risks / Trade-offs

- Полный baseline содержит ещё не реализованное поведение → В каждом change явно указывать implementation slice и не трактовать наличие требования как доказательство реализации.
- Демонстрационные профили содержат пустые A/B/C → Отклонять их сохранение по контракту и показывать точное место исправления.
- Ошибки могут устаревать после редактирования → Очищать или пересчитывать ошибку изменённого поля и повторять полную проверку при сохранении.
- Компонент редактора велик и связан → Ограничить extraction чистым валидатором и не выполнять широкий UI-рефакторинг.
- Клиентская проверка не является границей безопасности → Будущий backend save API обязан повторить те же правила перед постоянным сохранением.
- Обязательный production gate пока может быть неполным → Фиксировать отсутствующие проверки как blocker, а не объявлять change production-ready.

## Migration Plan

1. Зафиксировать независимый RED для текущего implementation slice.
2. Добавить валидатор и UI-feedback без изменения формата существующих данных.
3. Получить GREEN на focused tests и выполнить доступный регрессионный набор.
4. После реализации и подтверждения обязательного gate архивировать change; delta spec сформирует основную capability `vacancy-profile`.
5. Переносить остальные capabilities отдельными changes, сохраняя идентификаторы и статусы решений.

Откат реализации не требует миграции данных: постоянное хранилище ещё не участвует. Откат планирования выполняется до архивации возвратом артефактов change; после архивации изменения основной capability оформляются новым delta change.
