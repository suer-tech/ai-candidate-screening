## Purpose

Задать надёжную доставку исполняемых задач через RabbitMQ при сохранении PostgreSQL единственным источником истины для состояний, зависимостей, попыток и результатов обработки кандидатов.

## ADDED Requirements

### Requirement: RBQ-001 [CONFIRMED] PostgreSQL остаётся источником истины

RabbitMQ MUST использоваться только как транспорт уведомлений о готовых технических задачах. Канонические состояния кандидатов, запусков, задач, зависимостей, попыток, lease/fencing, checkpoints, артефактов и доступности повтора MUST храниться в PostgreSQL и MUST NOT восстанавливаться из содержимого очереди.

#### Scenario: Сообщение не является состоянием задачи
- **WHEN** consumer получает сообщение о задаче
- **THEN** он повторно читает задачу и её запуск из PostgreSQL
- **AND** выполняет её только после атомарного claim по идентификатору и версии
- **AND** подтверждает без исполнения устаревшее, уже завершённое или отменённое сообщение

### Requirement: RBQ-002 [CONFIRMED] Атомарная постановка и подтверждённая публикация

Перевод задачи в `RUNNABLE` и создание записи transactional dispatch outbox MUST выполняться в одной транзакции PostgreSQL. Publisher MUST публиковать persistent message в durable queue с publisher confirm и MUST отмечать outbox доставленным только после подтверждения broker. Неподтверждённые записи MUST публиковаться повторно.

#### Scenario: Сбой между commit и публикацией
- **WHEN** процесс завершается после commit состояния `RUNNABLE`, но до подтверждения RabbitMQ
- **THEN** недоставленная запись остаётся в dispatch outbox
- **AND** после восстановления publisher повторно публикует задачу
- **AND** задача не теряется и не считается выполненной

### Requirement: RBQ-003 [CONFIRMED] At-least-once без двойного эффекта

Consumer MUST подтверждать RabbitMQ delivery только после commit результата попытки в PostgreSQL. Redelivery MUST быть безопасным благодаря атомарному claim, lease/fencing token, проверке версии запуска и идемпотентным ключам внешних эффектов.

#### Scenario: Consumer падает после commit до ack
- **WHEN** результат задачи сохранён, но RabbitMQ не получил ack
- **THEN** сообщение доставляется повторно
- **AND** повторный consumer обнаруживает terminal task state
- **AND** подтверждает сообщение без повторного AI/provider-вызова и без повторной публикации результата

### Requirement: RBQ-004 [CONFIRMED] Ограниченные worker pools

Система MUST иметь durable routing для control, documents, media/transcription, LLM, reports, Drive и notifications. Для каждого pool MUST конфигурироваться положительная concurrency и bounded prefetch; broker MUST NOT выдавать одному consumer неограниченное число долгих задач.

#### Scenario: Одновременно готовы разные виды работ
- **WHEN** в очередях присутствуют document, transcription и LLM-задачи нескольких кандидатов
- **THEN** соответствующие pools могут выполнять их параллельно в пределах своих лимитов
- **AND** занятый media consumer не блокирует получение document или LLM-задачи другим pool

### Requirement: RBQ-005 [CONFIRMED] Повторы, poison messages и изоляция отказа

Момент следующего повтора и число попыток MUST определяться PostgreSQL. Невалидные envelopes и исчерпавшие допустимые доставки сообщения MUST направляться в dead-letter routing с безопасным error code. Отказ одной задачи MUST блокировать только зависящий от неё join и соответствующий запуск кандидата, но MUST NOT останавливать consumers или задачи других кандидатов.

#### Scenario: Одна shard-задача исчерпала повторы
- **WHEN** shard получает окончательную ошибку
- **THEN** её состояние и безопасный код фиксируются в PostgreSQL
- **AND** зависимый join и запуск получают наблюдаемую ошибку
- **AND** независимые кандидаты продолжают обрабатываться

### Requirement: RBQ-006 [CONFIRMED] Восстановление после недоступности broker

Readiness MUST различать недоступность RabbitMQ и недоступность PostgreSQL. При недоступном broker новые runnable-задачи MUST сохраняться в dispatch outbox; после восстановления система MUST переиздать их без ручного пересоздания запусков. Потеря очереди MUST допускать восстановление сообщений из PostgreSQL.

#### Scenario: RabbitMQ временно недоступен
- **WHEN** задача становится `RUNNABLE` во время недоступности broker
- **THEN** запуск не помечается завершённым или ошибочным только из-за невозможности публикации
- **AND** пользовательский статус отражает задержку инфраструктурной доставки
- **AND** после восстановления задача автоматически попадает в очередь
