## Context

См. `proposal.md` — Why. Текущий UI хранит редактируемый профиль и ABC-направления в состоянии `VacancySettings`, сохраняет их новой неизменяемой версией и уже имеет общий серверный RouterAI-контур генерации. Новое поведение затрагивает UI, версионируемую персистентность промптов, несколько структурированных LLM-операций и семантику ABC-валидации. Прямые вызовы провайдера из браузера и раскрытие секретов запрещены.

## Goals / Non-Goals

**Goals:**

- Использовать один согласованный черновик профиля для ручных и AI-изменений до явного сохранения.
- Обеспечить независимые, аудируемые и vacancy-scoped промпты для каждой операции.
- Сделать структурированные LLM-ответы детерминированно применимыми только к запрошенной области.
- Сохранить исторические версии и поведение существующих вакансий без backfill.

**Non-Goals:**

- Автосохранение сгенерированного текста или создание версии на каждый LLM-вызов.
- Миграция существующих ABC-направлений и описаний.
- Фоновая длительная job-модель для короткой генерации профиля.
- Возможность генерации поверх непустого отдельного поля.

## Decisions

### 1. Один серверный endpoint с типизированной операцией генерации

Запрос содержит vacancy id/version, тип операции (`field`, `abc`, `all`), точный prompt snapshot и минимальный структурированный input snapshot. Сервер авторизует доступ, проверяет размер и актуальность входа, вызывает RouterAI и валидирует operation-specific response schema. Для `field` ответ содержит ровно ключ и текст выбранного поля; для `abc` — массив `{id, gradeA, gradeB, gradeC}`; для `all` — полный поддерживаемый профиль.

Это уменьшает дублирование безопасности и трассировки по сравнению с отдельным endpoint на каждое поле, сохраняя строгую схему для каждой операции. Альтернатива со свободным текстовым ответом отклонена, потому что она не позволяет надёжно доказать область изменения.

### 2. Промпты сохраняются отдельно от несохранённого profile draft

У вакансии хранится отображаемая карта промптов по стабильным ключам четырёх полей и ABC-операции. Сохранение промпта — отдельное явное действие и не создаёт профильную версию; каждый LLM-run фиксирует точный prompt snapshot и идентификатор вакансии. Начальные значения детерминированно строятся из русских шаблонов с уже подставленным названием вакансии.

Отдельная персистентность выбрана потому, что пользователь ожидает применить исправленный промпт к следующему запросу до сохранения profile draft. Хранение только в браузере отклонено: оно нарушает vacancy isolation и теряется после перезагрузки.

### 3. Генерация изменяет только локальный draft

Успешный ответ применяется атомарно к соответствующей части состояния страницы и помечает draft dirty. Серверный LLM-run трассируется, но профильная версия не создаётся до штатного save. Ошибка, отмена подтверждения или невалидный ответ не меняют draft.

Для одиночного поля кнопка рендерится только при `trim() === ""`; после заполнения исчезает. ABC-кнопка доступна при наличии хотя бы одного направления и применяет результат по id, не по позиции или названию.

### 4. Защита навигации использует единый pending transition

Все управляемые переходы из настроек проходят через guard, который при dirty draft сохраняет намерение перехода и открывает один диалог. `Не сохранять` восстанавливает последний сохранённый snapshot и выполняет переход; `Сохранить изменения` ждёт успешного save и только затем выполняет переход; закрытие очищает pending transition без изменения draft. Для reload/close регистрируется стандартный `beforeunload`, поскольку браузер не разрешает кастомизировать текст и кнопки системного диалога.

Альтернатива с отдельной логикой для вкладок, боковой навигации и browser close отклонена из-за риска разных правил потери данных.

### 5. Новый ABC-шаблон меняется только в create boundary

Фабрика новой вакансии создаёт пять независимых standard-направлений в установленном порядке с пустыми `gradeA/B/C`. Репозиторий не выполняет миграцию существующих JSON-профилей. Валидация сохранения проверяет только стабильность id, непустые уникальные названия, origin и строковые типы описаний; пустой список допустим.

Assessment получает фактический versioned ABC snapshot. Направление без полного набора применимых определений не оценивается и не порождает A/B/C; отсутствие направлений означает отсутствие ABC-оценок, а не ошибку анализа.

## Risks / Trade-offs

- [Сохранённый prompt изменён одновременно в двух вкладках] → использовать optimistic version/precondition и возвращать конфликт без молчаливой перезаписи.
- [Ответ ABC не соответствует текущему составу] → требовать точное множество id и отклонять весь ответ атомарно.
- [Общая генерация уничтожает полезный draft] → отдельное явное предупреждение с перечислением полной перезаписи; отмена не вызывает API.
- [Dirty-state пропущен при программном изменении] → вычислять dirty сравнением нормализованного draft с последним сохранённым snapshot, а не набором ручных флагов.
- [Пустые ABC уменьшают полноту отчёта] → показывать «Недостаточно данных/правило не задано» и запрещать модели выдумывать определения.
- [Длительный запрос оставляет UI в неопределённом состоянии] → один in-flight запрос на операцию, disabled controls, finally-reset и понятная retryable ошибка.

## Migration Plan

1. Добавить backward-compatible хранение карты промптов с детерминированными defaults при отсутствии данных.
2. Развернуть типизированный generation endpoint и tracing до включения UI-действий.
3. Переключить create boundary на пустые ABC-описания только для новых вакансий.
4. Развернуть UI и новую валидацию одной совместимой версией приложения.
5. Проверить, что существующие вакансии читаются без изменений и новые создаются по новому шаблону.

Rollback возвращает прежний UI и create factory; новые записи с пустыми ABC должны оставаться читаемыми, поэтому rollback-версия перед откатом обязана принимать их как legacy draft и не выполнять destructive migration.
