## Context

В проекте одновременно существуют прежний набор нормативных требований и OpenSpec. Этот change переносит в OpenSpec 172 исходных требования семи областей и после согласования решений добавляет 5 самостоятельных требований (`ASM-024`, `ASM-060`, `ASM-061`, `TST-075`, `TST-076`), всего 177; ещё 25 требований `VAC-*` находятся в отдельном активном change `validate-vacancy-abc-profile`. Миграция должна сохранить исходные идентификаторы, статусы решений и смысл, не создавая ложного впечатления о готовности кода.

## Goals / Non-Goals

**Goals:**

- сделать каждую capability самодостаточной и проверяемой без внешнего нормативного текста;
- обеспечить однозначную сверку по стабильным ID;
- отделить подтверждённое поведение от TBD, assumptions и post-MVP;
- собрать вопросы реализации с владельцем, блокируемым этапом и безопасным поведением до ответа.

**Non-Goals:**

- изменение приложения, интеграций, схем данных или тестового кода;
- решение продуктовых TBD от имени владельцев;
- повторный перенос `VAC-*` или утверждение реализованности требований;
- удаление прежнего набора до архивации и проверки обеих миграционных changes.

## Decisions

### 1. Сохранять один исходный ID в одном Requirement

Каждый `PRD-*`, `WF-*`, `ASM-*`, `REP-*`, `INT-*`, `OPS-*`, `SEC-*` и `TST-*` представлен отдельным OpenSpec Requirement. Это позволяет машинно сравнить множества ID и не терять трассируемость. Альтернатива — объединить близкие правила — короче, но скрывает пропуски и смешивает статусы.

### 2. Статус является частью заголовка требования

`CONFIRMED`, `TBD`, `ASSUMPTION` и `POST-MVP` сохраняются явно. Для TBD сценарий задаёт только безопасную границу: не угадывать правило и не объявлять соответствующее качество принятым. Альтернатива — вынести все статусы только в общий реестр — затрудняет чтение capability отдельно.

### 3. Capability самодостаточна

Нормативный смысл и необходимые межфункциональные условия раскрываются в тексте и сценариях. Стабильные ID других требований могут использоваться как трассировка, но ни одна capability не требует чтения прежнего хранилища. Альтернатива — оставить ссылки — сохраняет два источника истины.

### 4. Открытые решения не превращаются в поведенческую capability

Вопросы собраны ниже как реестр решений: сами вопросы не являются поведением системы. После ответа соответствующий будущий change должен обновить затронутые specs и добавить/уточнить acceptance oracle. Альтернатива — создать capability `open-decisions` — смешивает требования и управление решениями.

### 5. Миграция завершается двумя согласованными changes

Эта change покрывает семь областей, 172 перенесённых ID и 5 новых ID из согласованных решений, всего 177; отдельная change вакансии покрывает 25 `VAC-*`. Прежние дубликаты можно убирать только после строгой проверки, review и синхронизации обеих changes с main specs. Альтернатива — дублировать VAC здесь — создаёт конкурирующие delta specs.

## Risks / Trade-offs

- [Сжатая формулировка может потерять нюанс] → перед архивацией провести смысловой review каждого ID, а не только автоматическое сравнение множеств.
- [Два активных migration change временно делят baseline] → архивировать/синхронизировать их согласованно и проверить итоговое покрытие всех 202 ID: 197 перенесённых и 5 добавленных по согласованным решениям.
- [TBD может быть ошибочно воспринят как реализуемая свобода] → сценарии явно запрещают домысливание и реестр называет блокируемый этап.
- [Внутренние ссылки между ID могут устареть] → стабильные ID не переиспользовать; изменение смысла проводить отдельным OpenSpec change.
- [Удаление прежних файлов раньше времени лишит контекста] → удаление является отдельным, проверяемым и обратимым шагом после архивации.

## Migration Plan

1. Проверить наличие всех семи capability, сохранность множества 172 переносимых ID и отдельное наличие 5 новых требований из согласованных решений.
2. Провести смысловой review формулировок, статусов и сценариев, отдельно проверив все TBD и assumptions.
3. Строго валидировать эту change и change `validate-vacancy-abc-profile`.
4. Синхронизировать или архивировать обе changes в согласованном порядке, затем проверить main specs на полный baseline из 202 ID.
5. Обновить карту проекта и инструкции агентов так, чтобы нормативным источником стал OpenSpec.
6. Только отдельным явно одобренным изменением удалить или заменить прежние дублирующие требования.

Rollback: до удаления прежнего набора достаточно откатить архивацию/синхронизацию migration changes. После удаления восстановить прежние файлы из истории Git и вернуть ссылки в карте проекта; данные приложения не затрагиваются.
