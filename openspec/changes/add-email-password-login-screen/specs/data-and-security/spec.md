## MODIFIED Requirements

### Requirement: SEC-002 [CONFIRMED] Авторизация единой роли MVP
Система MUST требовать серверную аутентификацию по корпоративной почте и паролю в локальном и production VPS-контурах. В MVP каждый авторизованный пользователь единой роли `HR-владелец вакансии` MUST иметь доступ ко всем вакансиям и кандидатам без ограничения по создателю или назначению. Неавторизованный пользователь MUST видеть брендированный экран входа и MUST NOT получать рабочие данные или выполнять операции. Principal MUST создаваться только после проверки активной учётной записи и валидной серверной сессии; недоверенный клиентский identity header MUST игнорироваться. Экран входа MAY показывать только синтетические обезличенные карточки и MUST NOT запрашивать кандидатские данные до успешной аутентификации. Google Drive OAuth MUST запускаться отдельно после входа. Опубликованный `chatgpt.site` MUST оставаться вне этого механизма и вне релиза данного изменения.

#### Scenario: Авторизованный HR открывает вакансию другого HR
- **WHEN** пользователь единой роли с валидной сессией запрашивает вакансию, созданную другим авторизованным HR
- **THEN** система разрешает просмотр и продуктовые операции MVP

#### Scenario: Пользователь не авторизован
- **WHEN** запрос без валидной сессии обращается к рабочей странице, вакансии, кандидату, результату или изменяющей операции
- **THEN** система не раскрывает данные и не выполняет операцию
- **AND** browser flow получает экран входа, а API получает `401`

#### Scenario: Клиент подделывает identity header
- **WHEN** внешний запрос передаёт `oai-authenticated-user-id` или другой недоверенный identity header без валидной сессии
- **THEN** локальный и VPS-контуры игнорируют заголовок и отклоняют запрос

#### Scenario: Неавторизованный пользователь видит композицию продукта
- **WHEN** открывается экран входа
- **THEN** декоративные карточки содержат только синтетические обезличенные значения
- **AND** браузер не запрашивает API кандидатов, вакансий, результатов или материалов

#### Scenario: HR подключает Google Drive
- **WHEN** авторизованный HR хочет подключить личный Google Drive
- **THEN** отдельный OAuth consent запускается из защищённой части приложения, а не из формы входа

## ADDED Requirements

### Requirement: SEC-011 [CONFIRMED] Закрытые password credentials
HR-учётные записи MUST создаваться только оператором без публичной регистрации. Email MUST сравниваться в канонической форме и быть уникальным. Пароль MUST содержать не менее 12 символов, MUST храниться только как memory-hard salted hash с версионированными параметрами и MUST NOT попадать в browser storage, логи, audit payload или обратимо зашифрованное хранилище. Временный пароль MUST требовать смены при первом входе. Отключённая учётная запись MUST терять доступ и все её активные сессии MUST отзываться. Initial HR MUST создаваться отдельной операторской командой без пароля в аргументах командной строки или source-controlled файлах.

#### Scenario: Оператор создаёт первого HR
- **WHEN** оператор запускает bootstrap-команду с email и получает пароль через защищённый интерактивный ввод
- **THEN** система создаёт активную учётную запись единой HR-роли с уникальным canonical email и password hash
- **AND** plaintext password не печатается и не сохраняется

#### Scenario: HR входит с временным паролем
- **WHEN** credentials верны, но учётная запись требует смены пароля
- **THEN** система разрешает только смену пароля и выход
- **AND** product UI и product API остаются недоступны до успешной смены

#### Scenario: Оператор отключает HR
- **WHEN** активная учётная запись отключается операторской командой
- **THEN** новые входы отклоняются, а все существующие сессии немедленно становятся недействительными

### Requirement: SEC-012 [CONFIRMED] Защищённые серверные сессии
После успешного входа система MUST выдать криптографически случайную непрозрачную сессию в host-only HttpOnly cookie с `SameSite=Lax`; production cookie MUST иметь `Secure`. В PostgreSQL MUST храниться только hash session token. Обычная сессия MUST иметь абсолютный срок 12 часов, а выбранное «Запомнить меня» — 30 календарных дней. Сессия MUST ротироваться после входа и смены пароля, MUST отзываться при выходе, отключении пользователя или операторском отзыве и MUST NOT приниматься после истечения. Изменяющие browser-запросы MUST дополнительно проходить same-origin и session-bound CSRF-проверку. Безопасный same-origin return path MAY восстанавливаться после входа; внешний либо протокольный return path MUST отклоняться.

#### Scenario: HR успешно входит
- **WHEN** активный HR отправляет правильные email и пароль
- **THEN** сервер создаёт новую сессию с непрозрачным cookie и возвращает безопасный профиль без password hash или session token

#### Scenario: HR выбирает «Запомнить меня»
- **WHEN** вход успешен и флаг выбран
- **THEN** абсолютный срок сессии составляет 30 календарных дней вместо 12 часов

#### Scenario: HR выходит
- **WHEN** HR подтверждает выход
- **THEN** текущая серверная сессия отзывается, cookie удаляется, а последующий product-запрос получает `401`

#### Scenario: Выполняется изменяющий запрос без CSRF-доказательства
- **WHEN** browser-запрос с session cookie изменяет состояние без допустимого same-origin и session-bound CSRF-доказательства
- **THEN** сервер отклоняет операцию с `403` и не изменяет данные

#### Scenario: Return path указывает на внешний адрес
- **WHEN** форма входа получает absolute, protocol-relative или иной неразрешённый return path
- **THEN** после входа система открывает безопасный маршрут по умолчанию внутри приложения

### Requirement: SEC-013 [CONFIRMED] Ограничение перебора и безопасные ошибки
Форма входа MUST возвращать одинаковое пользовательское сообщение для неизвестного email, неправильного пароля, отключённой и временно заблокированной учётной записи. После пяти неуспешных попыток в скользящем окне 15 минут система MUST блокировать дальнейшие попытки для сочетания canonical email и источника на 15 минут. Проверка несуществующего пользователя MUST выполнять сопоставимую password-hash работу. Логи и ответы MUST NOT раскрывать password, hash, cookie, session token, CSRF secret или факт существования email. Успешные и неуспешные входы, блокировки, выходы, смены пароля, отключения и отзывы сессий MUST записываться как безопасные audit events с UTC временем и actor/target identifiers без credential material.

#### Scenario: Введён неправильный пароль
- **WHEN** credentials не проходят проверку
- **THEN** пользователь видит общее сообщение «Не удалось войти. Проверьте данные»
- **AND** ответ не показывает, существует ли email

#### Scenario: Достигнут предел попыток
- **WHEN** для canonical email и источника накоплено пять неуспешных попыток за 15 минут
- **THEN** следующие попытки отклоняются в течение 15 минут без проверки реального пароля
- **AND** событие блокировки записывается в security-аудит

#### Scenario: Security-событие записано
- **WHEN** происходит вход, выход, смена пароля, блокировка, отключение пользователя или отзыв сессии
- **THEN** audit event содержит тип, безопасные идентификаторы, результат и UTC время
- **AND** не содержит credential или session material

### Requirement: SEC-014 [CONFIRMED] Единый auth-контур для Windows и VPS
Локальный Windows и production VPS MUST использовать одну PostgreSQL schema и одинаковые auth/domain правила. Local HTTP MAY устанавливать cookie без `Secure` только при явном loopback development mode; production MUST fail closed без HTTPS, session secret и актуальных migrations. Production nginx MUST удалять входящие app identity headers и MUST NOT подставлять постоянный HR principal. Явный E2E identity bypass MAY работать только при локальном E2E-режиме и MUST быть запрещён production preflight. Сброс забытого пароля в MVP MUST выполняться операторской командой через новый временный пароль с обязательной сменой; публичная email-доставка и самостоятельное восстановление не требуются.

#### Scenario: Локальный HR входит в приложение
- **WHEN** приложение запущено в разрешённом loopback development mode
- **THEN** оно использует PostgreSQL credentials и sessions по тем же правилам, что VPS
- **AND** допускает отсутствие `Secure` только у loopback session cookie

#### Scenario: VPS принимает внешний запрос
- **WHEN** nginx проксирует HTTPS-запрос в приложение
- **THEN** он удаляет пользовательские identity headers и не создаёт principal
- **AND** приложение определяет пользователя только по своей валидной сессии

#### Scenario: Production пытается включить тестовый обход
- **WHEN** production preflight обнаруживает E2E identity bypass либо отсутствие обязательного session secret
- **THEN** запуск завершается ошибкой до приёма пользовательского трафика

#### Scenario: HR забыл пароль
- **WHEN** оператор выдаёт новый временный пароль защищённой командой
- **THEN** прежние сессии отзываются, а следующий успешный вход требует смены пароля
