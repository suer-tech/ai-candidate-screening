# Рабочий реестр решений UI-аудита

**Статус: WORKING DRAFT / НЕНОРМАТИВНЫЙ ДОКУМЕНТ.**

Этот файл фиксирует подтверждённые владельцем продукта решения по результатам UI-аудита. Он не является main spec, proposal, design, tasks или delta spec и сам по себе не изменяет канонические требования OpenSpec.

## Подтверждённые решения

Владелец явно разрешил закрыть оставшиеся UI-вопросы наиболее обоснованными defaults. Они помечены `DEFAULTED BY OWNER AUTHORIZATION` и остаются ненормативными до reviewed change.

### Demo controls и status presentation

1. **DEFAULTED BY OWNER AUTHORIZATION.** No-op кнопки `Фильтры` и `Экспорт` в таблице кандидатов выбранной вакансии и no-op поиск `Найти вакансию` удаляются из MVP. Функциональные filters общей очереди и export конкретного PDF сохраняются. **Rationale:** main specs не задают vacancy-list export/search/filter, а неработающие controls создают ложное обещание.
2. **DEFAULTED BY OWNER AUTHORIZATION.** Human-readable labels canonical states: `Новый`, `Ожидание стабильности`, `Недостаточно материалов`, `Материалы готовы`, `Транскрибация`, `Анализ`, `Проверка результата`, `Готово`, `Ошибка`. Архив отображается отдельным lifecycle badge и не заменяет workflow status. **Rationale:** прямое отображение девяти canonical states не смешивает stage, recommendation и archive lifecycle.
3. **DEFAULTED BY OWNER AUTHORIZATION.** Основной badge всегда показывает status текущего input/run. После появления новых материалов или подтверждения reprocess прежний `READY` не остаётся основным badge и прежние результаты скрываются по подтверждённому правилу. **Rationale:** пользователь должен видеть текущее наблюдаемое состояние, а не устаревший success.
4. **DEFAULTED BY OWNER AUTHORIZATION.** `TRANSCRIBING` начинается при старте применимого STT stage; `ANALYZING` — при старте первого AI assessment call после готовности всех prerequisites; `VALIDATING` — после получения structured AI response и до завершения schema/evidence/PDF checks. **Rationale:** boundaries основаны на наблюдаемых stage events и не зависят от конкретного провайдера.

### Кнопка `На следующий этап`

1. Кнопка `На следующий этап` удаляется из MVP.
2. В MVP процесс приложения завершается на готовом кандидате и опубликованных отчётах и материалах, предоставленных HR для принятия решения.
3. Приложение в MVP не хранит кадровое решение HR и не вводит состояния hiring pipeline.
4. Возможность хранить кадровое решение HR и поддерживать hiring pipeline может быть рассмотрена после MVP только через отдельный reviewed OpenSpec change.

### Верхняя навигация `Аналитика`

1. В первом MVP раздел и пункт верхней навигации `Аналитика` полностью скрываются.
2. Интерфейс первого MVP не показывает для `Аналитики` состояние `Скоро`, disabled-control или иную demo-заглушку.

### Архивирование, восстановление и удаление кандидата

1. Кандидата нельзя архивировать, пока его workflow находится в processing, включая подготовку материалов, транскрибацию, анализ и валидацию.
2. Archive action остаётся недоступным и не выполняется до завершения processing.
3. Это правило исключает архивирование активного run и закрывает вопрос о его судьбе при archive action: такой переход во время processing не допускается.
4. Окончательное удаление кандидата доступно только после его архивации.
5. Окончательное удаление удаляет только данные приложения. Приложение никогда не удаляет папки или файлы Google Drive и не требует от HR удалять их вручную.
6. Отдельный status или очередь незавершённой Drive-cleanup не нужны. Любой ранее обсуждавшийся вариант с контролем удаления Drive-папки отменён.
7. Восстановление кандидата из архива обязательно записывается в аудит наряду с archive и delete.
8. **DEFAULTED BY OWNER AUTHORIZATION.** Archive находится в карточке кандидата, требует подтверждения и disabled во время processing с объяснением. Restore доступен из archive filter/card и выполняется без запуска анализа. Delete доступен только в архивной карточке, требует отдельного необратимого подтверждения и удаляет только данные приложения. **Rationale:** destructive actions имеют явные guards, а restore остаётся обратимой lifecycle-операцией.

### Ручный запуск повторной обработки

1. В карточке кандидата нужна отдельная кнопка ручного запуска повторной обработки.
2. HR использует её после изменения материалов в связанной папке кандидата Google Drive.
3. Само изменение файлов не запускает повторную обработку автоматически.
4. Ручной запуск создаёт новый run и новую версию результата по canonical version rules.
5. Кнопка показывается в карточке кандидата со статусом `READY` и в карточке кандидата со статусом `FAILED` после исчерпания автоматических повторов.
6. Пока текущая обработка продолжается, кнопка остаётся видимой, но disabled. Рядом или в доступном пояснении явно указано, что повтор станет доступен после завершения текущего запуска.
7. Нажатие доступной кнопки открывает confirmation dialog. Предупреждение сообщает HR, что предыдущие результаты станут недоступны и данные кандидата будут обновлены.
8. После явного подтверждения система сначала выполняет стандартную проверку стабильности файлов в связанной папке кандидата Google Drive.
9. Новая обработка автоматически запускается только после успешного подтверждения стабильности. До этого run не стартует.
10. Отмена dialog не запускает проверку или run и не изменяет данные кандидата.
11. Для этого поведения требуется отдельный reviewed OpenSpec change и согласованный UI flow до реализации.

## Ограничение применения

До подготовки и review соответствующего OpenSpec change этот working draft не изменяет main specs и не является основанием для редактирования proposal, design, tasks, delta specs или реализации кода.
