# Рабочий реестр решений MVP dashboard

**Статус: WORKING DRAFT / НЕНОРМАТИВНЫЙ ДОКУМЕНТ.**

Этот файл фиксирует подтверждённые владельцем продукта решения для будущей проработки dashboard. Он не является main spec, proposal, design, tasks или delta spec и сам по себе не изменяет канонические требования OpenSpec.

Владелец явно разрешил закрыть оставшиеся вопросы наиболее обоснованными defaults. Они помечены `DEFAULTED BY OWNER AUTHORIZATION` и остаются ненормативными до reviewed change.

## Подтверждённые решения

### Основная задача dashboard

MVP dashboard одновременно решает две операционные задачи:

1. Контроль текущей обработки кандидатов и ошибок.
2. Обзор готовых результатов кандидатов и статуса активных вакансий.

Обе части входят в назначение одного MVP dashboard и не являются отдельной post-MVP аналитикой качества работы рекрутеров.

### Блок `Контроль очереди`

1. Текущая визуальная структура и назначение блока `Контроль очереди` в веб-интерфейсе подходят для MVP и сохраняются.
2. Demo/static data должны быть заменены реальными данными canonical workflow.
3. Для каждого кандидата блок показывает фактические workflow stage/status и elapsed time.
4. Числовой ETA показывается только при выполнении всех условий canonical specs. Если условия не выполнены, вместо числа показывается точный текст `Недостаточно данных для прогноза`.
5. Сохранение layout не подтверждает текущие demo labels, hardcoded counts или расчёты времени.
6. Ошибки обработки показываются на dashboard только в этом существующем блоке очереди; подробное состояние также доступно в карточке кандидата.
7. Отдельный dashboard-блок ошибок, error summary, error list или error panel в MVP не создаётся.

### Малые summary cards кандидатов

1. Текущая визуальная структура малых summary cards под блоком очереди сохраняется для MVP.
2. Labels и counts каждой card строятся по актуальным canonical workflow statuses кандидатов без выдуманных упрощённых категорий.
3. Cards не показывают demo ratings, общий score или несуществующее в MVP состояние кадрового решения HR.
4. Текущая demo-card `Ожидают решения` и связанные с ней rating/decision формулировки не сохраняются как продуктовая семантика.
5. Primary cards отображают HR-facing canonical состояния: недостаточно материалов, exact processing stages, готово и ошибка; technical ожидание стабильности остаётся вне primary summary.
6. Точный layout не группирует processing stages и не должен менять canonical смысл.
7. **SUPERSEDED.** Прежний default с primary card `Ожидание стабильности` и общей card `Обработка` отменён явным решением владельца.
8. **CONFIRMED BY OWNER.** В той же группе вместо summary-card `Активные вакансии` показывается lifecycle-card `Архив`. Она считает всех архивированных кандидатов независимо от сохранённого workflow status, показывает `0` при пустом архиве, использует нейтральное тематическое оформление и открывает общую очередь с archive filter; empty state — `В архиве кандидатов нет.` `Архив` не является новым workflow status.
9. **CONFIRMED BY OWNER.** Semantic tones cards: недостаточно материалов — amber/yellow, `Транскрибация`/`AI-анализ`/`Проверка результатов` — distinguishable indigo/violet tones, готово — green, ошибка — red, архив — gray. Text label, count и exact filter semantics обязательны и не позволяют использовать цвет как единственный индикатор; recommendation palette остаётся отдельной.
10. **SUPERSEDED.** Кратковременное решение показывать `Проверка результатов` как отдельную primary card отменено явным уточнением владельца.
11. **SUPERSEDED.** Решение скрыть `Проверка результатов` и разнести `Транскрибация`/`AI-анализ` на отдельные cards отменено последним явным решением владельца.
12. **SUPERSEDED.** Решение объединить `Транскрибация` и `AI-анализ` в одну card отменено финальным явным решением владельца.
13. **CONFIRMED BY OWNER.** Primary dashboard показывает ровно семь отдельных cards: `Недостаточно материалов`, `Транскрибация`, `AI-анализ`, `Проверка результатов`, `Готово`, `Ошибка`, `Архив`. Processing counts и filters соответствуют exact `TRANSCRIBING`, `ANALYZING`, `VALIDATING` без объединения. `WAITING_FOR_STABILITY` остаётся technical state queue/detail без primary card. Семь cards адаптивно перестраиваются без изменения labels/counts/order.

### График `Поток кандидатов`

1. График `Поток кандидатов` сохраняется в MVP.
2. График отображает реальные данные вместо demo/static values.
3. Для dashboard-графиков доступен рабочий period selector со значениями `7`, `30` и `90 дней`.
4. Кандидат учитывается в графике в день успешного завершения обработки, а не в день первого обнаружения.
5. При повторной обработке каждый кандидат учитывается только один раз — по последней актуальной успешной версии результата; прежние result versions не создают дополнительных counts.
6. Если последняя повторная обработка завершилась `FAILED`, прежний successful result исключается из всех dashboard graphs и summary. До появления новой успешной актуальной версии ошибка кандидата показывается только в блоке `Контроль очереди` и карточке кандидата.
7. **DEFAULTED BY OWNER AUTHORIZATION.** График содержит отдельную series для каждой active vacancy и считает текущих неархивных кандидатов по дате завершения их последней актуальной успешной версии в `Asia/Yekaterinburg`. Период включает текущую дату и предыдущие `N-1` календарных дней; нулевые дни показываются как нули, отсутствие данных — как пустой график без demo values. **Rationale:** это продолжает фактический vacancy-series layout и исключает двойной учёт версий.

### Блок `Результаты анализа`

1. Блок `Результаты анализа` сохраняется в MVP.
2. Блок использует только четыре canonical recommendation categories: `Не рекомендовать`, `Недостаточно данных`, `Рекомендовать с оговорками`, `Рекомендовать`.
3. Блок не показывает проценты соответствия, общий score или demo labels вроде `Сильное соответствие` и `С рисками`.
4. Counts строятся из реальных результатов по canonical categories.
5. Кандидат с последней повторной обработкой `FAILED` не учитывается в recommendation counts до появления новой успешной актуальной версии.
6. **DEFAULTED BY OWNER AUTHORIZATION.** Блок использует тот же selector `7/30/90 дней`, считает текущих неархивных кандидатов с актуальным `READY` по дате завершения текущей успешной версии и позволяет перейти в очередь, отфильтрованную по выбранной canonical recommendation. **Rationale:** единая временная выборка делает dashboard-графики сопоставимыми и не создаёт отдельной скрытой метрики.

### Индикатор Google Drive

1. Индикатор Google Drive сохраняется в MVP dashboard.
2. Индикатор отражает реальное текущее состояние интеграции, а не demo/static status.
3. Система проверяет подключение к Google Drive каждые `15 секунд` и обновляет индикатор по результату проверки.
4. Индикатор имеет ровно три пользовательских состояния: `Подключён`, `Проверяем подключение`, `Нет подключения`.
5. **DEFAULTED BY OWNER AUTHORIZATION.** Индикатор не содержит ручных recovery-actions. `Проверяем подключение` показывается во время initial/in-flight проверки, `Подключён` — после успешной проверки, `Нет подключения` — после неуспешной. Следующий автоматический check выполняется через 15 секунд. **Rationale:** интеграция восстанавливается системным polling, а не неподтверждённой ручной операцией HR.

### Приветствие dashboard

1. Приветствие автоматически выбирается между `Доброе утро`, `Добрый день` и `Добрый вечер` по локальному времени `UTC+5`.
2. **DEFAULTED BY OWNER AUTHORIZATION.** В `UTC+5` используются границы: `Доброе утро` с 05:00 до 11:59, `Добрый день` с 12:00 до 17:59, `Добрый вечер` с 18:00 до 04:59. Приветствие использует display name текущего авторизованного HR. **Rationale:** это устойчивые непересекающиеся локальные интервалы без добавления четвёртой неподтверждённой категории.

### Очередь и остальные controls

1. **DEFAULTED BY OWNER AUTHORIZATION.** `Контроль очереди` показывает terminal errors первыми, затем активную обработку по времени старта от старой к новой; на dashboard выводятся первые пять записей и ссылка `Вся очередь`. **Rationale:** сначала видны требующие внимания ошибки, а ограничение сохраняет обзорный характер dashboard.
2. **SUPERSEDED.** Прежний default о card `Активные вакансии` отменён явным решением владельца.
3. **CONFIRMED BY OWNER.** Summary-card `Активные вакансии` отсутствует. Active vacancies остаются только источником series графика `Поток кандидатов`; её место в группе cards занимает `Архив` с archive-filter behavior.
4. **DEFAULTED BY OWNER AUTHORIZATION.** Отдельные dashboard filters, export, recruiter analytics, HR decision state и скрытые demo actions не добавляются. **Rationale:** они не входят в подтверждённый MVP scope.

## Ограничение применения

Открытых продуктовых вопросов в этом реестре не осталось. Перед реализацией все решения должны быть оформлены отдельным reviewed OpenSpec change; до этого main specs остаются каноническими.
