# Integrations and Operations Specification

## Purpose

Определить контракты Google Drive, транскрибации и AI-анализа, а также SLA, наблюдаемость и эксплуатационную надёжность конвейера.

## Requirements

### Requirement: INT-001 [CONFIRMED] Чтение Google Drive
Система MUST читать входные материалы из согласованной папки Google Drive через официальный API с минимально необходимыми правами.

#### Scenario: Получение материала
- **WHEN** система загружает входной файл
- **THEN** используется авторизованный официальный API в пределах выданных прав

### Requirement: INT-002 [CONFIRMED] Техническая идентичность объектов Drive
Для дедупликации файла система MUST использовать Google Drive File ID и его версию; для идентичности папки вакансии или кандидата — Google Drive Folder ID, связанный с внутренним UUID соответствующей сущности. Путь и имя MUST NOT быть достаточным идентификатором.

#### Scenario: Файл переименован
- **WHEN** прежняя версия файла получает новое имя
- **THEN** система не обрабатывает её как новый уникальный файл

#### Scenario: Папка переименована или перемещена
- **WHEN** путь папки меняется при сохранении Google Drive Folder ID
- **THEN** система сохраняет связь с прежней внутренней сущностью

#### Scenario: Создана копия папки кандидата
- **WHEN** новая папка имеет другой Google Drive Folder ID
- **THEN** система считает её новым кандидатом и создаёт новый внутренний UUID

### Requirement: INT-003 [CONFIRMED] Обнаружение папок
Система MUST опрашивать отслеживаемую структуру каждые 15 секунд и выявлять новые папки кандидатов.

#### Scenario: Появилась папка
- **WHEN** в отслеживаемой области создана папка кандидата
- **THEN** она обнаруживается очередным 15-секундным циклом

### Requirement: INT-004 [CONFIRMED] Изменения в отслеживаемой области
Система MUST корректно обрабатывать создание, переименование, перемещение, обновление и удаление входных файлов. Создание или изменение файлов в системном каталоге `Результаты/` MUST NOT считаться изменением входного комплекта.

#### Scenario: Входной файл изменён
- **WHEN** файл перемещён или обновлён
- **THEN** актуальное состояние отражается без потери его технической идентичности

#### Scenario: Опубликован выходной PDF
- **WHEN** приложение создаёт файл внутри `Результаты/vNNNN/`
- **THEN** сканер входных материалов игнорирует это событие
- **AND** не сбрасывает стабильность и не создаёт новый запуск

### Requirement: INT-005 [CONFIRMED] Владение Shared Drive и сервисный аккаунт
Рабочая структура MUST находиться в корпоративном Google Workspace Shared Drive и MUST NOT зависеть от личного диска или жизненного цикла учётной записи HR. Приложение MUST использовать отдельный сервисный аккаунт с доступом только к области `Найм`: чтение входных материалов и создание выходных отчётов без права управлять участниками Shared Drive. Учётные данные MUST поступать только из разрешённого секрета окружения.

#### Scenario: Приложение обращается к рабочей области
- **WHEN** production-компонент читает материалы или создаёт отчёт
- **THEN** запрос выполняется сервисным аккаунтом в корпоративном Shared Drive
- **AND** доступ ограничен областью `Найм` и необходимыми операциями

#### Scenario: Учётная запись HR отключена
- **WHEN** отдельный HR теряет доступ или увольняется
- **THEN** доступ приложения к рабочей структуре не прекращается

#### Scenario: Приложение пытается управлять участниками
- **WHEN** сервисный аккаунт запрашивает изменение состава участников Shared Drive
- **THEN** операция отклоняется его моделью прав

### Requirement: INT-006 [CONFIRMED] Минутные снимки
После обнаружения папки система MUST раз в минуту сохранять снимок ID файлов, количества файлов и размера каждого файла.

#### Scenario: Выполнена проверка готовности
- **WHEN** наступает минутный цикл
- **THEN** сохраняется полный снимок перечисленных атрибутов

### Requirement: INT-007 [CONFIRMED] Три стабильных интервала
Три последовательных минутных интервала без изменения количества и размеров MUST подтверждать завершение загрузки; любое изменение MUST сбрасывать счётчик в ноль.

#### Scenario: Изменился размер
- **WHEN** в период ожидания размер одного файла меняется
- **THEN** накопленная стабильность сбрасывается

### Requirement: INT-008 [CONFIRMED] Ошибка запроса не равна стабильности
Ошибка запроса Drive MUST NOT засчитываться как неизменность; интервал пропускается, а проверка повторяется следующим циклом.

#### Scenario: Drive временно недоступен
- **WHEN** минутный запрос завершён ошибкой
- **THEN** счётчик стабильности не увеличивается

### Requirement: INT-009 [CONFIRMED] Передача записи провайдеру
Система MUST скачать конкретную версию записи через авторизованный Drive API и передать содержимое по защищённому соединению; общедоступная ссылка MUST NOT публиковаться.

#### Scenario: Отправка на транскрибацию
- **WHEN** запись готова к обработке
- **THEN** провайдер получает защищённо переданное содержимое без публичной ссылки

### Requirement: INT-010 [CONFIRMED] Возможности транскрибации
Для интервью MUST использоваться асинхронная транскрибация длинных записей с таймкодами, уверенностью и разделением говорящих. После сохранения исходной диаризации LLM MUST автоматически сопоставить speaker-метки с ролями `Кандидат`, `Интервьюер` или `Другой участник` по содержанию диалога без подтверждения HR. Для каждого сопоставления MUST сохраняться роль либо `Недостаточно данных`, исходная speaker-метка, цитаты и таймкоды основания, модель и версия инструкции. Исходная диаризация MUST оставаться неизменной. Система MUST NOT определять роль или имя по акустической биометрии, полу либо иным голосовым признакам. Известное имя кандидата MUST браться только из карточки кандидата после сопоставления роли `Кандидат`.

#### Scenario: Длинное интервью
- **WHEN** запускается транскрибация поддерживаемой длинной записи
- **THEN** результат включает временную и спикерную структуру и уверенность

#### Scenario: Роли определены по содержанию
- **WHEN** диалог содержит достаточные явные основания для сопоставления говорящих
- **THEN** LLM сохраняет роль каждой применимой speaker-метки с цитатами и таймкодами без запроса подтверждения HR
- **AND** известное имя из карточки используется только для метки с ролью `Кандидат`

#### Scenario: Роль неоднозначна
- **WHEN** содержание не позволяет надёжно выбрать роль или содержит противоречивые основания
- **THEN** role mapping получает `Недостаточно данных`
- **AND** пользовательское представление сохраняет исходную метку `Спикер A/B`

### Requirement: INT-011 [CONFIRMED] Хранение исходника и структуры
Исходник MUST сохраняться в Google Drive, а в разработке MAY поступать из локальной `candidate`; система MUST хранить полный текст, реплики, слова, начальные/конечные таймкоды, ID говорящих и уверенность. Исходные speaker-метки провайдера и отдельное LLM-сопоставление ролей MUST храниться раздельно, чтобы role mapping не переписывал диаризацию. Таймкоды слов и реплик MUST оставаться относительными от начала записи и MUST NOT зависеть от календарной временной зоны. Абсолютные timestamps провайдера MUST нормализоваться в UTC ISO 8601, а переданная провайдером исходная зона MUST сохраняться в метаданных.

#### Scenario: Транскрипция сохранена
- **WHEN** провайдер вернул успешный результат
- **THEN** все перечисленные уровни данных доступны последующему анализу

### Requirement: INT-012 [CONFIRMED] Маркировка низкой уверенности
Исходный числовой confidence технического распознавания MUST храниться в диапазоне от 0 до 1 вместе с извлекателем, моделью и применённым порогом и MUST показываться пользователю в процентах. Для AssemblyAI слово MUST отмечаться низкоуверенным при confidence `< 0,7`. Реплика MUST отмечаться низкоуверенной, если средняя confidence её слов `< 0,7` или не менее 30% слов имеют confidence `< 0,7`. Цитируемый фрагмент MUST наследовать низкую уверенность реплики. Сводка MUST показывать долю низкоуверенных слов и реплик без автоматической общей категории «хорошая/плохая транскрипция». Порог AssemblyAI `0,7` и доля `30%` MUST поступать из конфигурации и MAY изменяться после калибровки отдельным change. Порог OCR MUST настраиваться отдельно для выбранной OCR-модели и MUST NOT неявно наследовать порог AssemblyAI.

#### Scenario: Слово ниже порога
- **WHEN** confidence слова меньше 0,7
- **THEN** нормализованный результат отмечает слово как низкоуверенное

#### Scenario: В реплике много низкоуверенных слов
- **WHEN** средняя confidence реплики не ниже 0,7, но минимум 30% её слов ниже 0,7
- **THEN** реплика и цитируемые из неё фрагменты отмечаются низкоуверенными

#### Scenario: Формируется сводка качества
- **WHEN** транскрипция нормализована
- **THEN** система рассчитывает долю низкоуверенных слов и реплик
- **AND** не присваивает всей транскрипции бинарную категорию качества

#### Scenario: Отображается confidence OCR
- **WHEN** доказательство получено OCR-моделью
- **THEN** пользователь видит исходный confidence в процентах и отметку относительно OCR-порога
- **AND** применённый OCR-порог сохранён вместе с моделью

### Requirement: INT-013 [CONFIRMED] Провайдер транскрибации MVP
MVP MUST использовать AssemblyAI Pre-recorded STT через `https://api.eu.assemblyai.com`, для русского интервью — `universal-2`.

#### Scenario: Русское интервью
- **WHEN** отправляется русскоязычная запись
- **THEN** запрос идёт на EU endpoint с моделью universal-2

### Requirement: INT-014 [CONFIRMED] Проверка медиаконтента
Система MUST принимать аудио и видео и определять контейнер и аудиодорожку по MIME, сигнатуре и метаданным потока, а не только расширению.

#### Scenario: Имя заканчивается на .08
- **WHEN** файл `Запись встречи 14.08` содержит поддерживаемое медиа
- **THEN** суффикс имени сам по себе не вызывает отказ формата

### Requirement: INT-015 [CONFIRMED] Извлечение аудио
Фоновый Node-процесс MUST извлекать первую аудиодорожку FFmpeg в M4A: совместимый AAC копируется, иначе преобразуется в AAC mono 48 kHz 96 kbit/s; видео, субтитры, data-потоки, главы и лишние метаданные MUST исключаться.

#### Scenario: Несовместимый кодек
- **WHEN** первая аудиодорожка не совместима с целевым контейнером
- **THEN** создаётся M4A с заданными параметрами AAC без остальных потоков

### Requirement: INT-016 [CONFIRMED] Параметры AssemblyAI
Запрос MUST содержать `language_code: "ru"`, `speech_models: ["universal-2"]`, `speaker_labels: true`, `punctuate: true`, `format_text: true`; `speakers_expected` MUST передаваться только при достоверном точном числе говорящих.

#### Scenario: Число говорящих неизвестно
- **WHEN** точное число не доказано
- **THEN** speakers_expected отсутствует и определение поручается сервису

### Requirement: INT-017 [CONFIRMED] Три представления транскрипции
После успеха система MUST сохранять полный ответ провайдера, нормализованный JSON `schemaVersion: 1` и читаемый текст со спикерами и таймкодами; нормализованный JSON MUST быть автономным контрактом последующего AI-анализа.

#### Scenario: Повторный анализ
- **WHEN** AI-анализ запускается по сохранённой транскрипции
- **THEN** ему не требуется повторный запрос AssemblyAI

### Requirement: INT-018 [CONFIRMED] Временное аудио, удаление и секрет
Извлечённое аудио MUST быть временным и удаляться после обработки, кроме явной диагностики; после атомарного сохранения локальных артефактов удалённая транскрипция MUST удаляться, ошибка удаления MUST иметь повторяемый статус; `ASSEMBLYAI_API_KEY` MUST поступать только из секрета окружения и не попадать в код, документы, результаты или логи.

#### Scenario: Удаление у провайдера не удалось
- **WHEN** локальные артефакты сохранены, но удалённая очистка дала ошибку
- **THEN** система фиксирует отдельный статус и допускает безопасный повтор без утечки ключа

### Requirement: INT-019 [CONFIRMED] Идентичность говорящих
Метки A, B и далее MUST считаться голосовыми ID, а не личностями; без отдельного доказательного шага компонент MUST NOT назначать им имена или роли.

#### Scenario: Роль неоднозначна
- **WHEN** материалы не доказывают соответствие голоса человеку
- **THEN** личность говорящего остаётся неизвестной

### Requirement: INT-020 [CONFIRMED] Структурированные схемы AI и OCR
Последующий AI-анализ MUST вызываться серверным компонентом через OpenAI-compatible API провайдера RouterAI и MUST возвращать результат по версионируемой структурированной схеме, а не только свободный текст. Каждый структурированный AI-ответ MUST содержать строковый `schemaVersion` формата `major.minor`. Добавление необязательных полей MUST повышать `minor`; удаление, переименование, изменение типа или смысла обязательного поля MUST повышать `major`. Каждая версия инструкции модели MUST быть привязана к ожидаемой версии схемы. Текстовый PDF MUST разбираться без OCR. Каждая страница сканированного PDF MUST передаваться серверным компонентом отдельной OCR-модели RouterAI через OpenAI-compatible API; OCR-ответ MUST содержать распознанный текст, номер страницы, координаты фрагментов и confidence. Модели анализа и OCR MUST настраиваться независимо. Конкретные base URL и модели MUST поступать из конфигурации и MUST NOT зашиваться в бизнес-логику.

#### Scenario: AI ответил
- **WHEN** анализ завершён
- **THEN** результат разбирается по известной версии схемы

#### Scenario: Схема расширена обратно совместимо
- **WHEN** к структурированному ответу добавляется необязательное поле без изменения существующей семантики
- **THEN** повышается `minor` версии схемы

#### Scenario: Контракт изменён несовместимо
- **WHEN** обязательное поле удаляется, переименовывается либо меняет тип или смысл
- **THEN** повышается `major` версии схемы

#### Scenario: Сервер вызывает RouterAI
- **WHEN** запускается AI-анализ кандидата
- **THEN** сервер использует настроенный OpenAI-compatible endpoint RouterAI и выбранную конфигурацией модель
- **AND** браузер не получает API-ключ или прямой провайдерский вызов

#### Scenario: Сканированный PDF требует OCR
- **WHEN** система обнаруживает страницу PDF без извлекаемого текстового слоя
- **THEN** сервер передаёт страницу отдельно настроенной OCR-модели RouterAI
- **AND** принимает структурированный текст с номером страницы, координатами и confidence

#### Scenario: PDF содержит текстовый слой
- **WHEN** текст страницы PDF можно извлечь напрямую
- **THEN** система не отправляет эту страницу OCR-модели

### Requirement: INT-021 [CONFIRMED] Проверка AI перед публикацией
Перед публикацией система MUST машинно проверить `schemaVersion`, обязательные поля, допустимые значения, доказательства, противоречия и стоп-факторы. Известная старая версия MUST преобразовываться в текущую внутреннюю схему только явным детерминированным адаптером; адаптер MUST NOT выдумывать отсутствующие обязательные данные. Неизвестная или неподдерживаемая версия результата кандидата MUST завершать этап `VALIDATING` состоянием `FAILED` с кодом `UNSUPPORTED_SCHEMA_VERSION`. Частичный результат MUST NOT публиковаться.

#### Scenario: Ответ невалиден
- **WHEN** в AI-результате отсутствует обязательное доказательство
- **THEN** результат не публикуется как успешный

#### Scenario: Получена известная старая версия
- **WHEN** для исходной `schemaVersion` зарегистрирован детерминированный адаптер
- **THEN** система создаёт текущую нормализованную форму
- **AND** не изменяет исходный ответ

#### Scenario: Версия схемы неизвестна
- **WHEN** RouterAI возвращает неизвестную или неподдерживаемую `schemaVersion`
- **THEN** кандидат переходит из `VALIDATING` в `FAILED` с кодом `UNSUPPORTED_SCHEMA_VERSION`
- **AND** ни один частичный отчёт не публикуется

### Requirement: INT-022 [CONFIRMED] Воспроизводимость AI
Система MUST отдельно для анализа и OCR сохранять провайдера RouterAI, фактические base URL без секретных параметров, идентификатор и доступную версию модели, версию инструкции, ожидаемую и фактическую `schemaVersion`, параметры запуска и ID входных материалов. Исходный ответ провайдера MUST сохраняться неизменным. Если применялись адаптеры, система MUST отдельно сохранять нормализованный результат и упорядоченную цепочку идентификаторов и версий миграций. Для файла, разобранного без OCR, метаданные MUST явно показывать, что OCR-модель не вызывалась.

#### Scenario: Аудит анализа
- **WHEN** исследуется версия результата
- **THEN** доступны все перечисленные сведения запуска, исходный ответ и цепочка миграций

#### Scenario: Аудит распознавания документа
- **WHEN** исследуется доказательство из сканированного PDF
- **THEN** доступна фактическая конфигурация OCR-запуска без секретов

### Requirement: OPS-001 [CONFIRMED] Наблюдаемый ориентир времени
Первая версия MUST использовать 30 минут после фиксации полного стабильного комплекта как желаемый показатель для наблюдения и оптимизации, а не гарантированный SLA, ошибку или release gate. Полное время стандартного анализа MUST включать ожидание в очереди, извлечение текста резюме и OCR при необходимости, извлечение аудио, транскрибацию, AI-анализ, валидацию, формирование и проверку двух PDF, сохранение в Google Drive и доставку Telegram-уведомления. Конечной точкой полного успешного измерения MUST быть первая успешная доставка уведомления хотя бы одному настроенному получателю; время до `READY` и время доставки после `READY` MUST измеряться отдельно. Окончательная ошибка Telegram MUST NOT отменять `READY`, а полное время до успешного уведомления для такого запуска MUST оставаться незавершённым с отдельным состоянием доставки.

#### Scenario: Начало измерения
- **WHEN** комплект признан полным и стабильным
- **THEN** начинается измерение фактического времени относительно 30-минутного ориентира

#### Scenario: Стандартный анализ успешно завершён
- **WHEN** оба PDF проверены и сохранены и первое уведомление успешно доставлено настроенному получателю
- **THEN** система фиксирует полное время стандартного анализа от момента готовности комплекта
- **AND** сохраняет отдельные длительности до `READY` и от `READY` до доставки

#### Scenario: Telegram не доставлен после READY
- **WHEN** отчёты готовы, а все попытки Telegram-доставки исчерпаны
- **THEN** кандидат сохраняет `READY`, время до `READY` остаётся доступным, а полное время до успешного уведомления помечается незавершённым

#### Scenario: Обработка длится больше 30 минут
- **WHEN** задание продолжает штатно выполняться после ориентира
- **THEN** система сохраняет метрику превышения и продолжает обработку
- **AND** не переводит задание в ошибку только из-за времени

### Requirement: OPS-002 [CONFIRMED] Калибровка времени по фактическим данным
Первая версия MUST собирать фактические длительности, размеры входов, параллелизм и внешние задержки без объявления продуктовых границ применимости SLA. После репрезентативного периода система MUST позволять рассчитать как минимум p50, p95 и долю обработок в пределах 30 минут. Обязательный SLA, нагрузочные границы и оптимизации MUST вводиться отдельным OpenSpec change.

#### Scenario: Анализируется первая версия
- **WHEN** накоплена выборка завершённых обработок
- **THEN** команда может определить p50, p95, долю в пределах ориентира и вклад каждого этапа
- **AND** эти данные сами по себе не превращаются в гарантированный SLA

### Requirement: OPS-003 [CONFIRMED] Тайм-ауты и повторы
Каждый этап MUST иметь конфигурационный тайм-аут, ограниченные повторные попытки и отдельный код ошибки. Стартовая конфигурация MUST задавать: Google Drive и короткие внешние запросы — 60 секунд и не более 3 попыток всего; FFmpeg — 20 минут и не более 1 повтора; ожидание результата задания AssemblyAI — 60 минут, а отдельные сетевые запросы к нему — 60 секунд и не более 3 попыток всего; OCR RouterAI — 3 минуты на страницу и не более 2 повторов; анализ RouterAI — 10 минут и не более 2 повторов; валидация и сохранение — 2 минуты и не более 3 попыток всего. Между доступными повторами MUST применяться задержки 5, 15 и 45 секунд в указанном порядке. Изменение этих значений по фактическим метрикам MUST выполняться конфигурацией и MUST NOT требовать изменения бизнес-логики.

Автоматический повтор MUST применяться только к сетевой ошибке, timeout, HTTP 429 или HTTP 5xx. Повреждённый либо неподдерживаемый обязательный файл, HTTP 4xx кроме 429 и невалидные входные или выходные данные MUST завершать этап без автоматического повтора. После исчерпания разрешённых попыток временной ошибки либо немедленно при постоянной ошибке обработка кандидата MUST перейти в `FAILED` и сохранить файл при применимости, этап, код причины, число попыток и последнюю безопасно очищенную техническую ошибку. Частичный отчёт и уведомление об успехе MUST NOT публиковаться. Ручной повтор MUST начинаться со сбойного этапа и переиспользовать результаты уже завершённых дорогих этапов при неизменных входных версиях; замена необрабатываемого обязательного файла MUST создавать новую версию входного комплекта по WF-014.

#### Scenario: Этап завис
- **WHEN** этап превышает свой тайм-аут
- **THEN** временная ошибка повторяется по конфигурационной политике и backoff
- **AND** после исчерпания попыток фиксируется `FAILED` с этапом и кодом причины

#### Scenario: Входной файл повреждён
- **WHEN** извлечение обнаруживает повреждённый или неподдерживаемый файл
- **THEN** кандидат получает `FAILED` без автоматического повтора и частичной публикации
- **AND** HR получает требование заменить материал и вручную запустить обработку новой стабильной версии комплекта

#### Scenario: Настройка уточнена по метрикам
- **WHEN** IT изменяет тайм-аут или число попыток в допустимой конфигурации
- **THEN** новая политика применяется без изменения бизнес-логики

### Requirement: OPS-004 [CONFIRMED] Метрики
Система MUST измерять время обнаружения, ожидание стабильности, ожидание в очереди, извлечение документов и OCR, извлечение аудио, транскрибацию, AI-анализ, валидацию, создание и проверку PDF, сохранение в Google Drive, время до `READY`, доставку Telegram после `READY`, полное время до первой успешной доставки, долю ошибок и число повторов. Для расчёта ETA система MUST сохранять версию конфигурации моделей и этапов, длительность записи, число OCR-страниц, фактические повторы, внешние задержки, настроенный параллелизм и длительности этапов. Выборка ETA MUST содержать только успешные обработки той же конфигурации за последние 90 календарных дней и MUST считаться достаточной при размере не менее 10. Для запуска без успешной доставки полное время до уведомления MUST храниться как незавершённое вместе с конечным состоянием доставки, а не подменяться временем до `READY`. Абсолютные timestamps MUST храниться в UTC ISO 8601. Длительности MUST вычисляться монотонными часами, а не разностью отображаемых локальных timestamps. Интерфейс MUST отображать абсолютное время в настроенной зоне `Asia/Yekaterinburg` с явным `+05:00`; изменение зоны отображения в серверной конфигурации MUST NOT изменять сохранённые UTC-значения или рассчитанные длительности.

#### Scenario: Обработка завершена
- **WHEN** задание приходит в конечное состояние
- **THEN** перечисленные метрики доступны для наблюдаемости

### Requirement: OPS-005 [CONFIRMED] Операционное уведомление
Окончательный сбой MUST создавать уведомление ответственному пользователю. Превышение 30-минутного ориентира MUST фиксироваться в метриках и отображаться через прошедшее время, но MUST NOT само по себе создавать уведомление HR или ошибку задания.

#### Scenario: Ориентир превышен без сбоя
- **WHEN** анализ длится больше 30 минут и продолжает выполняться
- **THEN** HR видит текущий этап и прошедшее время без отдельного уведомления об ошибке

#### Scenario: Обработка окончательно завершилась ошибкой
- **WHEN** ограниченные повторы исчерпаны и задание перешло в конечную ошибку
- **THEN** ответственный пользователь получает уведомление

### Requirement: OPS-006 [CONFIRMED] Фоновая среда медиаобработки
FFmpeg и синхронное ожидание AssemblyAI MUST выполняться вне Cloudflare Worker в фоновом Node-процессе с временным диском и секретами; веб-приложение MAY запускать и отслеживать задание, но MUST NOT выполнять FFmpeg в request lifecycle.

#### Scenario: Загружено видео
- **WHEN** веб-приложение принимает задание
- **THEN** оно передаёт медиаобработку фоновому Node-процессу
